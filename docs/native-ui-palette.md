# 原生界面的位图调色板基线

原生属性商店、普通商店、装备研究、职业和学校考试的 BMP 表面，不能把文件内的像素索引直接当作显示表面的索引。`0x4589c0 → 0x45cf40 → 0x45d150` 先通过 `LoadImageA(0x2010)` 读取文件，再 `StretchBlt(SRCCOPY)` 到尚未设置独立调色板的 8 位 DirectDraw 表面。该步骤按构造时的显示色表转换索引。后续 FLC 的调色板更新作用于已经转换好的表面。

`0x456d30` 的反编译签名缺少一个参数。实际机器码的 `ret 0x0c` 及 `GetEntries` / `SetEntries` 调用表明，它接收文件路径、首项、末项，并从源调色板的同一索引区间复制到目标，未平移源色表。三个老板的原始范围分别为属性商店 `142..161`、普通商店 `142..161`、装备研究 `212..231`。保留这些范围；直接扩大到源 BMP 的 `202..221` 会改变原程序操作。

固定现代 Windows GDI 观察显示，属性商店老板的源索引 `202、203、210` 转换为 `7、77、88`，普通商店对应转换为 `248、247、237`，装备研究对应转换为 `232、245、243`。这解释了省略构造转换时出现的黑色轮廓。这些数值由实际 GDI 调用取得，不是为消除黑色轮廓选取的近似色。

`0x458b20` 在表面构造之后把数值 `1` 设为 `SetColorKey`。因此数值透明键必须在索引转换之后检查；例如普通商店某些分类按钮的源索引 `1` 会转换为 `247`，不能先把所有源索引 `1` 删除。采用首像素作为透明键的场景，同样使用转换后的首像素索引。

构造时序也影响映射。装备研究的图标由 `0x43cf70` 在 `yes_a.flc` 的 `163..200` 色表安装之后创建，早于研究动画的 `2..161` 色表安装，因此与初始背景、老板和模式按钮使用不同的构造色表。学校考试的 BMP 在 `0x43e030` 中创建；随后 `0x43f1a0` 安装主持人 `163..254`，`0x43f1bc` 再安装确认动画 `163..200`。考试结果阶段另用原结果动画的色表。

`tests/fixtures/original-native-ui-gdi.json` 保存六种构造上下文、151 张 BMP 的源哈希、完整目标色表、索引映射、完整图像哈希、黑底透明合成校验和，以及相关原始指令字节。Rust 的 `native_bmp_surfaces_match_all_fixed_gdi_observations` 通过实际 `ImageBank` / `PixelCanvas` 核对所有像素，包含三帧按钮条的每一帧。以下检查只依赖提交的资源与样本，不需要原 EXE 或 Windows：

```sh
node tools/export-native-ui.mjs --check
node tools/export-native-school.mjs --check
```

在 Windows 上，`python tools/export-native-ui-gdi.py --check` 可按原调用参数重新观察。需要先准备本地原始 EXE 与资源；不打开窗口或切换显示模式。上述证据与参数页已有的 GDI 基线一致，属于现代 Windows 的可复现兼容基线，尚不能替代 Windows 9x 原游戏 GUI 的完整逐帧截图对照。
