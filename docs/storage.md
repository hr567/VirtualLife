# Bevy 网页版存档

本次重构使用新格式和独立数据库。旧网页版本与 Windows 原版存档不兼容；客户端不读取、迁移或导出旧网页数据库。

## 数据库与文件

IndexedDB 数据库为 `virtual-life-bevy`，数据库版本为 2。`saves` 表以 `slot` 为键保存 `slot-0` 至 `slot-8` 共 9 个位置；`settings` 表单独保存音量等选项。素材的 CacheStorage 与存档数据库相互独立。

浏览器记录及导出文件使用以下外层字段：

```text
format: virtual-life-bevy-save
version: 1
savedAt: 保存时间
contentId: 当前规则内容标识
payload: Rust 核心存档及 Bevy 场景状态的 JSON 字符串
checksum: payload UTF-8 字节的 SHA-256
```

数据库记录另有槽位字段。Rust 核心的 payload 也带格式、版本、内容 hash、状态 checksum 和完整业务状态；外层文件校验通过后，核心仍会检查状态结构、地图坐标、活动记录、物品数量、随机数等约束，再执行恢复。

Bevy 在 payload 的 `presentation` 字段保存镜头、原生界面选择与计时、动画帧和未完成的行走表现，全部字节受外层 SHA-256 校验保护。恢复时先校验表现结构，再移除此字段并交给核心严格验证领域存档；成功后重建显示和音频实体。按住的物理输入、IME 和测试输入不会恢复。

原事件的中间背景、人物进退场、生日与工资提示以及新人生开场也保存在表现队列中。恢复会校验队列类型、长度、帧索引和影片状态；可见展示结束前不接受后续玩法命令，也不会按暂停期间的墙钟时间追帧。

内容标识根据解析后的规则目录规范化生成，统一对象键顺序、整数浮点表示与负零。实际规则内容变化会使旧内容标识失效，不通过忽略版本或校验值强行接受存档。格式字符串与旧客户端不同，即使版本号都为 1 也不互通。

## 保存与恢复

`F6`、主菜单“继续游戏”和系统菜单的保存、读取入口打开统一的画布内存档管理。槽位 0 是自动存档，槽位 1–8 是原版数量的手动槽位。选中槽位后可以读取，手动保存仅允许写入 1–8；所有 9 个位置都可导入、导出。导入只写入指定位置，留在存档界面，不改变正在玩的进度。覆盖已有手动记录或导入覆盖需要确认。

每次有效的普通投骰或指定点数投骰，在引擎消耗随机数和执行移动之前，将完整游戏及表现状态自动保存到槽位 0，覆盖该槽且不影响 1–8。打开点数选择菜单不保存。等待保存期间暂停玩法，写入成功后执行本次投骰；失败则显示提示并继续投骰，保留旧记录。不会在建角、其他操作、隐藏页面、返回菜单、轮回或显卡故障时自动写档。导入到槽位 0 的内容会在下次投骰前被覆盖。

同一连接按调用顺序串行写入。SHA-256 在事务外计算，手动覆盖在事务内核对列表读取时的记录，发生跨页面冲突则提示并刷新列表；事务失败保留原记录。请求编号将保存结果与一次待执行投骰关联，重复及过期回调不能再次投骰；后台收到结果会等待页面恢复后继续。

首次升级到数据库版本 2 时，在版本升级事务内将旧 `current` 和 `previous` 分别转入手动槽位 1、2，并移除旧键；内容与时间保持不变，槽位 0 初始为空。任何迁移写入失败都会回滚完整升级。此迁移仅针对 Bevy 新客户端数据库，不涉及旧网页数据库或 Windows 存档。

读档和文件选择结果按请求编号接收；切换页面或发起更新的读档后，迟到的旧结果被丢弃。自动保存失败以非阻塞提示显示，存档管理显示保存、导入、导出结果及错误。

导入文件限制为 8 MiB，并检查格式、时间字段、内容标识和 SHA-256；随后由 Rust 核心检查完整状态。导出只从新数据库取出经过校验的记录。不要手动修改 payload、hash 或 checksum 作为“修复”手段。

## 故障与更新

存储配额不足、事务失败或浏览器不允许 IndexedDB 时会报告错误；仍已提交的记录应保留。损坏记录可尝试其他槽位或外部导出文件。清除网站数据、浏览器清理策略或用户删除配置文件会删除本地记录，因此重要进度需要另存导出文件。

素材缓存写入失败不删除存档，也不阻止联网读取。Service Worker 更新应用壳时不清空新存档数据库。显示设备丢失会暂停运行，故障页提供 9 个槽位的导出选择；刷新页面重建 WebGPU 设备后，恢复以最近一次成功提交的自动或手动记录为准，未保存的进度无法恢复。
